# technical-blog-generator

用于把"指定技术主题"自动检索为多篇社区文章素材，并转化为可信、可读、可发布的小红书技术推文。

核心原则：
- 不捏造事实、不编造代码、不虚构收益数据。
- 风格要有吸引力，但不过度营销，不夸张承诺。
- 先产出草稿并询问是否发布；未得到明确同意前，禁止执行发布动作。

## 输入要求

开始执行前，至少收集以下信息；缺失时先追问：
1. 技术主题（必填，例如"RAG 检索优化""Python 异步任务调度"）
2. 目标读者（如后端开发、前端工程师、AI 应用开发者）

可选输入：
- 用户指定参考链接（如有则优先纳入分析）
- 期望字数（默认 600-900 中文字）
- 语气偏好（理性拆解/经验复盘/踩坑避坑）
- 是否包含原理图（默认根据具体场景自行判断）

## 执行流程（必须按顺序）

### 第 1 步：基于主题检索与证据台账

1. 基于用户给定主题，使用搜索与网页抓取工具检索候选文章（优先近一年、内容完整、技术细节充分的来源）。
2. 至少筛选 2-5 篇高相关内容进行阅读与交叉核验；若用户给了参考链接，则必须纳入。
3. 抽取以下事实并形成结构化"证据台账"：

```
## 证据台账

### 1. 核心论点
- 论点：xxx
- 来源：[文章标题 + URL] 第X段 "原句摘录..."
- 置信度：高/中/低

### 2. 支撑论据
- 论据：xxx
- 来源：[文章标题 + URL] 第X段 "原句摘录..."
- 类型：事实/数据/案例
- 置信度：高/中/低

### 3. 关键数据
- 数据：xxx
- 来源：[文章标题 + URL] 第X段 "原句摘录..."
- 置信度：高/中

### 4. 不确定表述
- "xxx"（来源：[文章标题 + URL] 第X段）— 作者使用了"可能""有些情况下"等限定词，改写时必须保留

### 5. 关键词清单
从来源文章中提取以下三类关键词，后续标题、正文、标签必须覆盖：

产品/项目名：涉及的具名产品、项目、组织名
核心概念/范式：提出的专有概念或方法论
关键平台/资源：给出的独立网址或平台名

### 6. 行动号召识别
从来源文章中识别所有推广性质的呼吁（CTA），单独列出：
- 号召内容：xxx
- 来源：[文章标题 + URL] 第X段
- 类型：下载使用 / 参与共建 / 上传分享 / 关注社区 / 其他
```

**规则**：
- 每条台账必须附原文引用，不允许凭印象归纳
- 置信度标准：高=原文明确陈述，中=原文暗示或可合理推断，低=仅有碎片信息
- 不确定表述必须单独列出，改写时作为约束条件
- 若文章带有明显宣传/发布属性，在拆解阶段必须同步抽取"发布来源/发布主体/配套发布内容"三项信息
- 对工具、平台、能力的职责边界要单独记录，避免在改写时把多个能力顺滑地合并成一个功能包

若检索结果信息不足，必须明确标注"来源未给出"，不要补写主观猜测。

### 第 2 步：判断是否需要源码验证

出现以下任一情况时，必须下载源码辅助分析：
- 原文包含具体实现描述，但表述模糊或可能有歧义。
- 需要给出"如何使用/如何启动/demo case"，但原文仅有结论无步骤。
- 用户明确要求"结合代码分析"。

源码验证要求：
1. 使用 `bash` 下载仓库（如 `git clone`）并定位关键文件。
2. 使用 `read_file` 阅读关键代码/README，提炼可被验证的结论。
3. 在证据台账中补充源码依据，写明"依据了哪些文件/命令结果"。

禁止在未查看源码时写出具体函数名、配置项、启动参数等细节。

### 第 3 步：判断帖子类型与配图策略

在写正文前，必须先判断这次更适合哪一类小红书帖子骨架，再决定文案节奏和配图方案。不要把所有题材都写成同一种“技术博客”。

推荐至少支持以下 5 类：

1. **教程清单类**
   - 适用于：技巧合集、最佳实践、使用建议
   - 结构：一句话痛点 → 一句话收益 → N 条技巧列表 → 一句收束
   - 媒体：封面大字 + 分页技巧卡
   - 参考特征：清单感强，正文允许 ❶❷❸ 编号，重点是“马上能用”

2. **实践体验类**
   - 适用于：产品试玩、真实上手、值不值得、demo 体验
   - 结构：个人/朋友切口 → 痛点 → 怎么用 → 看到的效果 → 适合谁/值不值
   - 媒体：界面截图、结果截图、关键流程截图
   - 参考特征：第一段先给使用场景，再给体验结果，代入感强

3. **技术解读类**
   - 适用于：论文解读、版本更新拆解、产品能力分析
   - 结构：为什么值得讲 → 这次重点是什么 → 关键点 3-6 条 → 结论
   - 媒体：封面大标题 + 图表/结论页
   - 参考特征：信息密度高，但不能变成论文摘抄，要先讲“这次最值得看什么”

4. **科普概念类**
   - 适用于：新概念解释、范式演进、术语扫盲
   - 结构：为什么最近总被问 → 概念是什么 → 跟旧概念的关系 → 为什么现在重要
   - 媒体：封面问题句 + 分页解释卡
   - 参考特征：先讲“为什么今天值得讲”，不能只给定义

5. **新闻 / 活动类**
   - 适用于：功能更新、活动预告、发布快讯
   - 结构：一句话消息 → 亮点 bullet → CTA / 时间地点 / 参与方式
   - 媒体：官方海报或封面图优先，正文可极短
   - 参考特征：更依赖封面和标签完成传播，正文不强制长文

判断后，在后台输出一个简短摘要（不要混进最终成稿）：
- 本次帖子类型：教程 / 实践 / 解读 / 科普 / 新闻活动
- 判断理由：xxx
- 推荐配图策略：封面图 / 截图 / 图表 / 海报

### 第 4 步：生成小红书草稿（不发布）

按本技能定义的标题、正文、文风规则填充。

模板结构：
- 通用规则：标题、主旨、文风、标签、宣传链接
- 分类模板：教程清单类 / 实践体验类 / 技术解读类 / 科普概念类 / 新闻活动类 / 深度技术博客子模板
- 证据清单附录

**小红书标题规则**（参考 article-atomize）：
- 标题必须是一个可单独成立的完整句，不能用"最近了解到一个项目"这类泛开场充当标题
- 如果原文属于发布/上线/开源/推出类内容，标题应显式包含"发布""上线""开源"等事件词，强化发布感
- 标题要直接说清楚发现了什么/差异在哪里/结果有多强，不要把信息留到正文里
- 避免公式化反差句式，如"不是 X 而是 Y"——这种表达读起来偏模板感，能直接陈述就优先直接陈述
- 优先使用"一句话创建""刚发布"这类强信息词，但情绪词必须服务于正文核心机制
- 标题要有信息量但不能像标题党，准确反映内容
- 标题不能过长，整体长度不能超过20字符

**小红书正文规则**：
- 开头：一句话交代这篇只讲一个什么判断或发现。直接给核心认知，不在铺陈中慢慢靠近
- 中段：每段 2-3 句，用 emoji 做视觉分隔。每一段都必须服务于同一条主线
- 结尾：一句回扣开头主旨的 takeaway
- 正文动笔前，先在内部分配一句"一句话主旨"，用它来检验每一段是否服务同一个重心
- 先按帖子类型选写法骨架，再填正文内容：
  - 教程清单类：清单结构优先，正文允许编号 ❶❷❸，重点是“马上能用”
  - 实践体验类：第一段必须先给痛点或使用场景，再给体验结果；允许更强代入感
  - 技术解读类：允许更强信息密度，但要先讲“这次更新最值得看什么”
  - 科普概念类：必须交代“为什么这个概念最近值得讲”，不能只给定义
  - 新闻/活动类：正文可以短，但 CTA、时间、地点、参与方式必须清晰

**小红书文风规则**：
- 采用用户/开发者第一视角，分享感强，像一个发现了好东西忍不住分享的朋友
- 短句为主，单句不超过 25 字
- 口语化但不水，避免"绝绝子""YYDS""太酷啦"等空洞感叹
- 主动回避"不是……而是……""重点来了""真正拉开差距的是……"等公式化转折句——这类句式的 AI 模板感太重
- emoji 用于分段标记，每段 1-2 个，不要连续堆砌
- 技术术语保留，但紧跟一句大白话解释（"即……""简单说就是……"）
- 不做虚假"亲身经历""我朋友""我试了"等编造叙事——如果原文是别人的案例，就说"有人试了""案例里"
- 用具体场景代替抽象描述：不说"效率很高"，说"以前要手动配半天，现在一句话搞定"
- 如果某篇承担的是"结构解析"角色，正文里仍可适度补入"怎么创建/怎么上手"的信息

**实践/案例类稿件额外要求**：
- 除了讲创建过程和协作机制，必须补一段"展示效果"：读者看完需要知道屏幕上具体看到了什么、为什么值得发
- 允许的展示效果（必须回源可证）：
  - 生成出的角色/配置/结构长什么样
  - 运行时过程有哪些节点可见
  - 最终输出的结果形态
  - 与手动操作相比省掉了哪一步
- 禁止只讲机制对不对，不讲最后看到了什么

**宣传链接规则**：
- 如果来源文章带有宣传/发布属性，正文末尾（标签前）应补入宣传链接
- 链接来源：来自台账关键词清单中的关键平台/资源项
- 覆盖策略：每篇至少覆盖一条链接；如果正文未提及 Hub，则同时补 Hub 地址并加一句简短介绍
- 链接必须来自来源文章明确给出的地址，不编造

**话题标签**：
- 3-5 个，格式 `#标签名`，放在正文末尾
- 标签必须覆盖台账关键词清单中的产品名和核心概念，不可遗漏
- 组合策略：产品名 + 核心概念在前（精准搜索），领域泛标签在后（泛流量）

以上规则在写作前一次性读入，写作时逐条对照。

### 第 5 步：文本质量检视与事实自检

草稿产出后，先做两轮自检再进入发布确认。

**文本质量检视**（检查项）：
- 语病：缺主语、缺谓语、搭配不当、句式杂糅
- 错别字：同音错字、形近错字
- 通顺度：句子是否拗口、虚词堆叠
- 标点：中英文标点混用、引号不匹配
- AI 句式：是否有"不是……而是……""重点来了""答案来了"等公式化转折句
- 重复表达：相邻句子语义重复
- 语义冗余："联合...共建""目的是为了"等句式

每条问题必须给出明确的修改建议，修正后正文必须是完整可发布的。

**事实自检**（检查维度）：
- 事实可追溯、数据可追溯、案例可追溯
- 因果关系准确、限定词保留、无新增推断
- 网址/平台名准确、平台声称可验证（如声称"在 GitHub 发现"需先验证该内容确实存在）
- 发布来源完整、功能边界准确、比较/归纳有依据

修正后输出完整自检报告。

### 第 6 步：图片与原理图策略

**优先级顺序**：来源图 > AI 生图 > Mermaid 原理图，配完图片后需要发送给用户

#### 6.1 检查图片生成 API 配置

在需要生成配图时，首先检查系统是否配置了图片生成 API：

```bash
python scripts/generate_image.py --check
```

返回结果：
- `{“available”: true, ...}` → 可使用 AI 生图
- `{“available”: false, ...}` → 无 API 配置，退回到 Mermaid 原理图

#### 6.2 图片获取策略

1. **优先复用来源图**（若来源文章已有可用图）：
   - 在文案里标注”图来自来源文章”
   - 路径中的空格用 `%20` 编码

2. **AI 生图**（若来源无图但 API 可用）：
   - 使用脚本 `scripts/generate_image.py` 生成配图
   
   **⚠️ 重要：默认调用两次图片生成，让用户选择最佳结果**
   
   **双次调用流程**：
   
   **第一次调用**：传入帖子原文（标题 + 正文完整内容）
   ```bash
   python scripts/generate_image.py      --prompt "帖子原文..."      --output "输出路径/cover_v1.png"
   ```
   
   **第二次调用**：传入转换后的提示词（适用于文生图的样式）
   
   **提示词转换规则**：
   - 将帖子内容转换为"场景化视觉描述"
   - 结构：`[场景设定] + [主体内容] + [文字元素] + [风格要求]`
   - 场景设定：描述图片所处的环境（如"一幅简约科技风海报置于干净现代空间"）
   - 主体内容：提取帖子的核心主题和关键信息
   - 文字元素：将标题、关键词转化为海报上的文字布局
   - 风格要求：指定整体视觉风格（如"专业简洁""科技感""古典中式"）
   
   **转换示例**：
   
   转换前（原帖）：
   > openJiuwen发布Team Skills规范，多Agent协作终于能沉淀了。多智能体协作一直有个痛点：每次任务结束，协作经验就丢了。Team Skills把协作协议变成了可移植、可分发的资产。五组件结构：frontmatter机器可读元数据定义角色工具模型，roles每个角色的详细persona，workflow任务依赖图，bind执行边界，evolutions演化经验自动记录每次改进。Leader Agent负责拆解任务分配给Teammates监控进度，Teammates主动认领任务独立执行汇报结果。案例：10个Agent各负责20页PPT，20分钟内拼出200页技术文档。
   
   转换后：
   > 一幅简约科技风智能体主题海报置于干净现代空间，桌面摆放极简数码设备，海报主标题为 openJiuwen 发布 Team Skills 规范，左侧文字 “多 Agent 协作沉淀经验”，右侧文字 “技能资产可移植分发”，横批 “智协进化”，字体利落科技感，中间绘抽象多智能体协作示意图，展现 Leader Agent 分配任务、Teammates 执行汇报，标注五组件结构与 10 个 Agent 高效产出 200 页文档案例，整体专业简洁。
   
   ```bash
   python scripts/generate_image.py      --prompt "转换后的提示词..."      --output "输出路径/cover_v2.png"
   ```
   
   **用户选择**：
   - 展示两张图片给用户
   - 询问："请选择用于小红书帖子的封面图：1. 原帖内容生成  2. 转换后内容生成"
   - 根据用户选择，将对应图片加入最终帖子
   
   **禁止做法**：
   - ❌ 只调用一次图片生成
   - ❌ 不让用户选择就直接使用某一张
   
   **正确做法**：
   - ✅ 默认调用两次图片生成
   - ✅ 让用户选择最佳结果
   - ✅ 转换提示词时参考上述示例格式
   
3. **Mermaid 原理图**（若无来源图且 API 不可用）：
   
   **⚠️ 重要：直接传入帖子原文，自动生成 Mermaid 图，并插入到小红书草稿原文**，
   
   **生成规则**：
   - 来源：第 4 步已生成的小红书草稿（标题 + 正文完整内容）
   - 直接传入：把帖子原文作为输入，无需手动设计图表结构
   - 自动处理：
     1. 从帖子内容中提取关键结构（组件、角色、流程、关系）
     2. 选择合适的图表类型（flowchart、sequenceDiagram、classDiagram 等）
     3. 生成符合小红书风格的简洁 Mermaid 代码
   
   **图表类型选择**：
   - 有组件/模块结构 → `flowchart TB` 或 `classDiagram`
   - 有交互/协作流程 → `sequenceDiagram` 或 `flowchart LR`
   - 有状态变化 → `stateDiagram`
   - 有层级关系 → `flowchart TB` + subgraph
   
   **正确做法**：
   - ✅ 直接传入帖子原文（标题 + 正文完整内容）
   - ✅ 自动提取关键结构，生成 Mermaid 代码
   - ✅ 图只表达核心流程，不堆砌细枝末节
   - ✅ 生成 Mermaid 代码后，插入到帖子原文

#### 6.3 小红书媒体资源规范

按帖子类型选择配图策略：
- **教程清单类**：封面优先用”大标题 + 品牌元素 + 收益点”，内页优先分页技巧卡，每页 1-2 条技巧
- **实践体验类**：优先真实界面截图、结果截图、前后对比截图；次选流程图或概念封面；禁止只给抽象配图不给使用结果
- **技术解读类 / 科普类**：封面优先大标题直给主题；内页优先图表、结论卡、对比卡；若引用技术报告，优先保留关键表格或图表
- **新闻 / 活动类**：优先官方海报或封面图；正文不强制长文，更重要的是亮点和报名/参与信息
- 实践向/案例向帖子默认应有配图，不建议做成纯文字长帖
- 优先策略不是自动抽帧，而是在成稿中写”建议从哪个视频截哪一类画面”
- 如果视频截图效果不理想，再退回到 AI 生图方案

#### 6.4 脚本说明

`scripts/generate_image.py` 支持以下功能：
- 自动检测 `.env` 中的 `IMAGE_GEN_API_KEY/IMAGE_GEN_API_BASE` 或 `VISION_API_KEY/VISION_API_BASE`
- 支持 DashScope 和 OpenAI 兼容格式（ModelArts 等）
- 返回 JSON 格式结果，便于后续处理

**参数说明**：
- `--prompt`: 图片生成提示词（必填，可以是帖子原文或摘要，由外部 agent 决定）
- `--output`: 输出图片路径（必填）
- `--size`: 图片尺寸（可选，默认 1024x1024）
- `--check`: 仅检查 API 配置是否可用

**注意**：脚本不做任何提示词预处理，直接传入原始内容调用图片生成 API。

# 贡献指南

感谢你有兴趣为这个项目贡献力量！无论是报告 bug、提新词库、改进文档，还是优化算法，我们都欢迎。

## 工作流程

### 第 1 步：反馈类型确认

在贡献前，先确认你的反馈属于哪一类：

| 类型 | 定义 | 处理方式 | 快速通道 |
|---|---|---|---|
| 🔴 **词库遗漏** | 某个高风险词应该被检查但没被抓到 | Issues > 月审 > 合并 PR | 高优先级 |
| 🟡 **误报修复** | 检查出的问题判断错了 | 提供复现案例 + 修复 PR | 高优先级 |
| ✏️ **改法优化** | 建议的改写方案更简洁/自然 | Issues 讨论 > 更新词库 suggestions | 中优先级 |
| 🆕 **新规则** | 发现词库覆盖不到的新风险模式 | 需要≥3 真实案例 + semantic 补充 | 中优先级 |
| 📖 **文档改进** | 说明文档、示例、注释等 | 直接 PR | 低优先级 |

### 第 2 步：提交反馈或 PR

#### 选项 A：通过 Issues 提交反馈（推荐新手）

1. 打开 [Issues](../../issues) → 新建 Issue
2. 选择对应的 Issue 模板（词库遗漏 / 误报 / 改法 / 新规则）
3. 按模板填写信息
4. 提交

**模板示例**：

```markdown
【反馈类型】词库遗漏

【问题描述】
「弹幕返利」组合词常见于未报备分销商单

【真实案例】
> 现在弹幕功能也有返利，有朋友已经在赚 5000+ 一个月

【为什么有问题】
「返利」+ 「赚钱」话术组合是分销商单特征，但当前 affiliate_hint 正则没覆盖「弹幕」

【建议方案】
在 banned_words.json signals 里补充 `弹幕` 或优化正则为：
`返利|返现|佣金|提成|分成|招代理|做代理|拿货价|一件代发|赚差价|分销|弹幕`

【相关证据】
- 小红书分销规范：所有返利内容需蒲公英报备
- 用户反馈（GitHub Issue #15, #22）也提到过
```

#### 选项 B：直接提交 PR（推荐开发者）

1. Fork 项目
2. 创建特性分支：`git checkout -b feat/add-banned-word-xxx`
3. 修改文件（见下面的"修改指南"）
4. 提交 Commit：`git commit -m "feat: add 弹幕 to affiliate signals"`
5. Push 到你的 Fork
6. 打开 Pull Request，描述改动原因 + 相关案例

PR 命名规范：
- `feat: xxx` — 新增词库、新规则
- `fix: xxx` — 修复误报、优化正则
- `docs: xxx` — 文档更新
- `refactor: xxx` — 代码重构

## 修改指南

### 场景 1：新增词库词语

**文件**：`scripts/banned_words.json`

```json
{
  "id": "absolute",
  "name": "绝对化用语（广告法）",
  "risk": "high",
  "words": [
    "全网第一",
    "新增词语放这里"  // ← 在这里追加
  ],
  "suggestions": {
    "新增词语": "改为非绝对化的表述"  // ← 同时加改法建议
  }
}
```

**检查清单**：
- [ ] 新词是否真的是违禁词或易限流词
- [ ] 有≥2 个真实案例作证明
- [ ] 添加了 `suggestions` 里的改法建议
- [ ] 改法建议不能只是删除，要提供可替换的表述
- [ ] 测试一遍，确保新词被正确检测

### 场景 2：新增正则模式

**文件**：`scripts/banned_words.json` 的 `patterns` 部分

```json
{
  "id": "wechat_emoji",
  "name": "微信导流变体（emoji 替代）",
  "risk": "high",
  "why": "站外导流，emoji 替代是常见的变体形式",
  "regex": "加.*?我.*(v|微|薇)[❤❣💗]",  // ← 你的正则
  "suggestion": "改为「欢迎站内私信」，删除一切站外联系方式"
}
```

**检查清单**：
- [ ] 正则表达式在 Python 中能正常编译和匹配
- [ ] 测试过真实案例，确保不误报
- [ ] 在注释里说明这个正则为什么需要
- [ ] 提供了改法建议

### 场景 3：语义规则补充

**文件**：`references/semantic-checks.md`

在对应的"判定自问"里补充：

```markdown
## 五、新的风险类型（如果有）

**定义**：...

**判定自问**：
1. 是否...
2. 是否...

**正例（违规）**：「具体违规文案」
**反例（安全）**：「改正后的文案」

**改法模板**：...
```

**检查清单**：
- [ ] 定义清晰，能让 Agent 理解
- [ ] 提供了≥3 个真实案例（正例 + 反例）
- [ ] 改法模板具体可执行，不是模棱两可的建议

### 场景 4：修复误报

**问题示例**：「最好的朋友」被误判为绝对化用语

**修复步骤**：

1. 在 `check_note.py` 的 `scan()` 函数或正则中加前后文检查
2. 或在 `rules.md` 里标注哪些是常见误报
3. 补充测试用例，推荐在 `scripts/test_check_note.py` 中增加

```python
from check_note import scan
import json
from pathlib import Path

db = json.loads(Path(__file__).resolve().parent.joinpath('banned_words.json').read_text(encoding='utf-8'))
text = "最好的朋友来帮我"
hits = scan(text, db)
assert not any(
    h["category"] == "绝对化用语（组合形式）" and h["matched"] == "最好"
    for h in hits
)

text = "这是全网最低价"
hits = scan(text, db)
assert any(
    h["category"] == "绝对化用语（广告法）" and h["matched"] == "全网最低价"
    for h in hits
)
```

**PR 说明**：清楚地描述：
- 为什么这是误报
- 你的修复方案
- 新增的测试用例

## 审核标准

贡献被合并的条件：

| 反馈类型 | 采纳条件 | 拒绝原因 |
|---|---|---|
| 词库遗漏 | ≥2 用户反馈 + 官方文件证据 | 缺证据 / 样本太少 / 不确定是违规 |
| 误报修复 | 提供复现案例 + 修复验证 | 无法复现 / 改动影响其他规则 |
| 改法建议 | 改法保留原意 + 更简洁 | 改后语义变了 / 安全性降低 |
| 新规则 | ≥3 真实案例 + 清晰规律 | 案例不足 / 规律不明确 |
| 文档 | 改进清晰 / 没有技术错误 | 文档更新与项目状态不符 |

## 月度审核流程

每月 1 日，维护者会：

1. 查看所有待审核的 Issues 和 PR
2. 按照「审核标准」逐条评审
3. 对符合条件的反馈评论 ✅ 或 ⏳（等待更多反馈）
4. 对不符合条件的反馈解释原因
5. 合并符合条件的 PR
6. 更新 CHANGELOG.md
7. 发布新版本

期间可能会要求你补充信息或测试用例，这是正常的互动。

## 代码规范

### Python 代码

- PEP 8 风格
- 类型注解（推荐）
- 函数有 docstring
- 注释用中文（与项目风格一致）

### JSON 配置

- 2 空格缩进（与现有 banned_words.json 一致）
- **JSON 不支持注释**——说明性文字放 `notes` 字段或分类的 `why` 字段（本文档示例代码里的 `//` 仅为图示，实际文件中不能出现）
- 避免 trailing comma

### Markdown 文档

- 标题用 `#` 而不是 `---`
- 代码块标注语言（`python`, `json`, `bash` 等）
- 中文和英文之间空一格
- 重点用 `**粗体**` 或 `> 引用` 突出

## 常见问题

### Q: 我的反馈多久能被处理？

**A**: 每月初统一审核（通常 3-7 天内）。高优先级的反馈（词库遗漏、明显误报）会优先处理。

### Q: 如果我的反馈被拒绝了怎么办？

**A**: 我们会在 Issue 或 PR 上详细说明原因。如果你有异议，可以继续讨论。有时候是因为需要更多证据或用户反馈，不一定是永久拒绝。

### Q: 我可以直接修改 SKILL.md 吗？

**A**: 可以，但建议先在 Issues 里讨论，因为 SKILL.md 涉及 Agent 使用说明，改动需要确保兼容性。

### Q: 我想加一个全新的功能（比如图片识别）应该怎么办？

**A**: 这属于「新产品」而不是「迭代优化」。建议在 Discussions 里先发起讨论，或在 Issues 里标记为 `feature-request`，社区可以集体评估。

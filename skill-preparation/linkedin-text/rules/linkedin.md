# LinkedIn 普通动态候选规则

适用 `platform=linkedin`、`format=short_post`、产出对象 `kind=linkedin_post`。候选版本 `linkedin-text-candidate.0.2.1`；尚未替换生产 `text-v1.0.0`。中文、英文各为一个独立普通 feed 动态。Pulse 正文、串帖、轮播文档、视频和其他平台不在本轮适配范围。

## 在共同母稿上改写

平台改写发生在共同母稿之后、本地化之前。读取同一 `claimLedger`、`termLedger` 与作者约束；选出对这批目标读者最有用的一条主张及其必要依据。不能从零生成一套新事实，也不能把长文章逐节缩成宣传摘要。

形成可独立阅读的论述：开头让读者知道讨论的具体问题或判断，随后交代理解所必需的背景，说明主张如何由事实或机制支持，最后落到实际用途或适用边界。这是内容要素，不是必须逐句套用的五段模板。根据目的选择：解释类优先机制与用途；更新类优先实际变化及影响；观点类优先立场及依据。故事只在材料确有作者经历时使用。

把读者相关性写具体：能帮助他判断什么、在哪种工作中使用、哪种条件下不适用。若材料只支持功能，不补出节时、降本或成功率收益。稿件在不点开外链时也应表达完整核心意思；链接用于让读者查看材料或下一步，不替正文承担全部解释。

保留母稿中把主张讲成立的解释，而非只抽取结论与名词。平台化是重新分配读者注意力：必要机制可以占主要篇幅，操作路径只写本次目的需要的部分。不要把资料中的每个限制都列成结尾；所保留主张的实质条件必须保留，无关的核查事项放回元数据。记录主要取舍及其理由，不以变短本身证明改写成功。

压缩例子时，保留决定结果的细节与主张之间的联系，次要枚举可以先退让。收束应完成本次论述：读者据此如何理解、选择或行动，而非换一句抽象话复述开头。需要保留检查条件时，让它解释实际决定；不额外强加建议、CTA或缺证据的结果保证。

精简顺序为：删除重复与包装语 → 合并重复背景 → 去掉不支持主线的次要信息 → 缩短句子。任何一步都不得删掉会改变判断的条件、比较基线、限制或责任主体。仍无法在上限内表达时记录冲突，不擅自改成 Pulse、续帖或外链摘要。

## 四类依据必须分开

| 类别 | 本轮采用的处理 | 证据边界 |
|---|---|---|
| 官方硬限制 | 普通动态上限 3000 字符；对最终发布文本预检 | LinkedIn Help 于 2026-09-24 实读；没有解释复杂 Unicode 的实际计数算法，也没有本轮提交实测 |
| 官方建议 | 开头体现观点或要点；短段落便于阅读；内容体现作者知识、观点与真实经验 | 官方 Talent Blog 的编辑建议与 AI 内容帮助建议，不是必须满足的 API 字段或审核认证 |
| 社区经验 | 借鉴单一主线、独立阅读价值、证据接主张、占位符与模板泄漏检查 | Corey、Sergey、Krzysztof 的经验经取舍后使用；不承诺流量或检测器结果 |
| 项目选择 | 纯文本发布正文；不强制 CTA、标签、故事、数字或固定段落数；每语言审核一次后统一修订 | 由本项目范围和创作目的决定，不能标成 LinkedIn 官方要求 |

来源与精确版本见 [来源清单](../sources.md)。官方建议即使鼓励 CTA，也不覆盖用户尚未确认 CTA 输入与默认的决定。官方建议在重度使用 AI 且上下文不明显时保持透明；审核可列为作者决定事项，不能自动加免责声明或阻断生成。

## 开头、正文和收束

- 开头直接表达这篇的观点、变化或具体问题。不能只说“发布了文章”“很高兴宣布”而不说明内容；若作者确需公告，保留公告目的并把具体变化提前。不要凭空制造反常识、戏剧冲突或个人回忆。
- 段落按一个完整意思划分，用空行帮助阅读；短段落是建议，不把每句断行、固定句数或固定长度当检查配额。保留句子之间真实因果和转折。
- 用技术名词时结合读者知识解释一次；不能为了“好懂”替换指定术语。列表仅在并列项更易比较时使用，不为满足模板强造三个要点。
- 最后一段完成论述，可是用途、判断或边界；只有本次目的与已有材料支持时才采用自然问题或下一步。没有 CTA、标签、emoji 或第一人称经历不构成缺陷。
- 正文以真实可发布的纯文本交付；内部标题、来源索引、审核标签和解释留在工件元数据。避免把 Markdown 标题、加粗标记、链接语法、模型引文标记或占位符泄漏为正文。此处纯文本为项目输出选择，不据此宣称全部 LinkedIn 编辑器均无格式能力。
- 外链有合适上下文且目标正确即可；不得因为“外链压流量”强制移至评论。不增加未经授权的 @ 提及或向他人发消息。

## 字符预检

对实际最终正文原样计数，包含空格、换行、实际 URL、标签与 emoji；内部标题、审核和素材 brief 不计入，除非它们实际进入发布正文。分别记录 `codePointLength = [...text].length` 与 `utf16Length = text.length`，并记录文本 hash。不要用英文词数推算中文长度，不把用户可见字形数当任一计数的等价物。

字段按阶段契约解释：`internalLabel` 仅用于界面，不计数；document 的非空 `title` 会参与当前发布拼接，必须计数。锁定且要求入帖的标题不能改标内部标题来绕过上限。body 已含标题的实验格式只计其实际整串一次。

本地候选采用保守预检：任一计数超过 3000 时标 `length_conflict` 并修订；两个计数均不超过时仅标 `local_length_checked`。该双计数策略是项目选择，不宣称它就是平台算法；组合 emoji、代理对、换行处理及平台最终接受结果仍待真实接入验证。提交时还需由发布适配器基于同一正文复核，本轮不调用发布。

不采用 140／150／210／265 字符作为通用“展开前”硬阈值，不强制 800–1800、900–1300 或 1200–1500 的“最佳”长度。社区规则之间相互冲突，且客户端、语言、布局不同；开头是否独立清楚由人工语义审核判断。

## 进入一次审核的检查项

| ID | 一次审核检查 | 不通过时的修订方向 |
|---|---|---|
| LI-01 | 对象是否仍是普通 feed；正文可独立读懂 | 去掉依赖未提供长文的指代；对象冲突进入未解决项，不冒充 Pulse |
| LI-02 | 一条主线是否在开头可辨；后文是否兑现开头 | 调整顺序、删掉旁支，避免仅把功能罗列成广告 |
| LI-03 | 事实、作者观点、计划是否分别表达；每个收益主张有无证据 | 回到母稿证据定位，删除无依据的新主张或准确保留未知 |
| LI-04 | 读者能否理解用途、机制和必要边界 | 补足材料中已有解释，不补造经历、性能或反常识 |
| LI-05 | 本地化后是否仍有完整限定与指定术语 | 在本语言修复措辞，并标出与其他语言共有的问题 |
| LI-06 | 纯文本、链接目标、字符计数、占位符和模型痕迹 | 在保真前提下改正文并重算；字符通过不等于平台审核通过 |
| LI-07 | 是否硬套 CTA、标签、故事、禁词或算法经验 | 去掉无任务依据的结构强迫，保留作者实际表达 |

上述项目与核心、本地化、作者检查合并到同一次审核记录；不另开“LinkedIn 再审”。共同事实问题进入统一修订计划，语言特有问题只改对应稿。修订后可做字符与 hash 等机械核对，不启动新一轮模型评分。终态是待用户确认候选，不能写成“可直接发布”“平台已通过”或传播保证。

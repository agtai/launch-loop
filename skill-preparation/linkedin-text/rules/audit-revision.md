# 一次审核与统一修订

状态：候选，尚未接入生产。规则版本：`linkedin-text-candidate.0.2.1`。阶段：`audit → revise → awaiting_confirmation`。审核产物不是用户批准、正式保存或 LinkedIn 平台审核通过。

## 调度约束

固定流程为 `intake → mother → platform → localize → audit → revise → awaiting_confirmation`。先冻结所有已选平台 × 语言初稿和共同来源；每份稿执行一次内容审核，审核集合齐后统一处理发现并修订。不得先为一个语言连续多轮润色，再用它改写另一个语言。母稿和平台改写不另建审核轮次。

对某份稿的审核只能引用该次冻结稿、母稿、共同 `claimLedger`／`termLedger`、其他语言的冻结稿和实际资料。只读这些输入，输出问题记录，不在审核中偷偷改正文。跨语言比较属于这一次审核的维度；不要在审核集合后再发起“跨语言总审”。

输入缺失、正文未生成、规则无法解析时记 `audit_not_run` 及原因，不能伪造空问题列表。审核调用技术失败可按相同输入 hash 重试，只有一份成功审核被接受；已经有有效审核结果时不再调用第二次内容审核。失败的尝试仍保留执行记录。

状态特例以 contracts 为准：正常创作在 intake 已阻断时，audit 作为下游阶段只记 `not_run_blocked`，不创建审核记录；`audit_not_run` 仅用于已经请求进入审核、此时发现所需输入缺失的情况。两者都表示没有内容审核发生，不能计为一次成功审核。

独立评测/用户明确只审已有稿时，可以仅审核所给稿件，但至少需要实际稿件、适用规则及用于判断的来源或已标明缺失状态；没有母稿或另一语言稿，就将对应同源/跨语维度标 `not_assessable`，不编造中间工件，也不声称验证了完整创作链路。这不增加正常生成流程的审核轮次。

## 一次审核清单

对所有项检查上下文后再报告；无具体问题可以没有 finding，不凑数量，不编评分。

在这一次审核中，先按目标读者的知识背景通读冻结正文，写一条简短 `readerTakeaway`：正文实际上让读者理解了什么。再对照输入目的与 `editorialPlan`，不能只复述作者原计划作为正文达标的证据。下面的编辑判断与事实检查一起完成，不能拆成第二轮润色。

| 编辑判断 | 需要给出的正文证据 |
|---|---|
| 相关性与目的 | 哪个实际片段使读者知道本次内容与自己有关；若只报产品名/特性而未完成解释，定位缺失关系两侧的文字 |
| 选择与篇幅 | 哪些内容承担主张和必要支撑；是否有次要操作、重复或旁支挤掉理解所需信息，删除/合并是否会损失条件 |
| 推进与完整性 | 从开头到结尾如何逐步形成判断；是否有概念跳跃、重复起步或收束偏题；短文已完成目的则无需强加例子和段落 |
| 声音与自然表达 | 哪处体现作者有依据的取舍/立场，哪处具体句法、指代或材料汇报语气妨碍阅读；没有个人故事不算问题 |

记录 `editorialAssessment`，对各维度给 `adequate / needs_revision / not_assessable`、真实片段或位置及简短依据。`adequate` 需要说明正文怎样完成目的，不以“无事实错误”“长度合格”替代。若问题成立，转成下面的 finding；缺资料不能评的部分明示。评价是可反驳的编辑判断，不是数值质量分，也不要求每个维度都产生问题。

判断推进时，要解释引用的段落之间怎样相连，而不只是确认每种信息都出现过。例子是否真的支持后面的判断；“适用性”是否有材料可支持的判断依据；结尾是否比开头多交付了一点理解。句子通顺且事实正确，仍可能缺少完成本次目的的关键联系。这类缺口有具体正文和读者影响时，按其影响报告，不能一概当作可忽略的风格偏好；只是另一种同样成立的写法则不要要求改。

| 检查维度 | 审核时要回答的问题 | 问题依据 |
|---|---|---|
| 主线、目的、读者 | 开头到结尾是否服务输入目的；解释粒度是否适合目标读者；是否偏离母稿 `spine` | 输入和母稿，而非“爆款公式” |
| 事实与承诺 | 每条事实是否能关联来源和 `claimId`；数字、适用范围、比较条件、完成状态是否保留 | 来源快照、主张台账；文档陈述不等于实测 |
| 跨语言保真 | 是否遗漏或扩大条件、否定、概率、责任主体；同一术语是否漂移 | 母稿、术语表及另一语言的冻结稿 |
| 作者表达 | 身份、立场、犹豫和作者明确保留表达是否还在；有没有编造经历 | 作者／产品规则和参考稿用途 |
| LinkedIn 普通动态 | 最终拼接正文是否在平台规则范围；段落、链接、图片 brief 是否适配普通 feed | 组合中的 LinkedIn 规则及其证据类型，不把社区经验当硬限制 |
| 残留与表达 | 是否有占位符、无意义重复、模板残留、空泛指代；删改是否会损失独有判断 | 具体位置与上下文，不按禁词命中判错 |
| 图文一致 | 正文和图片／配图 brief 的能力、数字、流程、术语和语言标注是否相容 | 已上传图片的实际内容或尚未生成的 brief；区分二者 |

必要补查可在本次审核中读取授权范围内的资料并记录新来源；仍不能访问时明确缺口。不得把“没有附来源”直接写成“虚假”，也不能把不明来源论断去掉归属后当事实。禁止运行 AI 检测器、预估传播分数或声称平台认可。

## 发现格式

每条 finding 至少具有以下信息，字段名是本候选协议，不声称既有服务已经支持：

- `findingId`：本次运行唯一，后续修订用该 ID 关联。
- `variantId / documentId / blockId / location`：精确到冻结正文；`location` 含选中引文及 UTF-16 `[start,end)`。跨段问题列出全部相关位置，标题问题用 `field: title`。
- `quote`：真实存在于该版本中的片段，禁止编造引文。
- `category / severity`：如 `fidelity / evidence / terminology / purpose / hierarchy / coherence / voice / platform / residual / image`；严重性用 `blocking / important / optional`。仅作为修改优先级，不能等同发布权限。
- `reason`：哪里偏离要求、影响了哪一语义；避免“读起来不好”而不给原因。
- `basis`：`sourceIds / claimIds / termIds / ruleIds` 及必要的证据位置；来源不可访问则明示。
- `suggestedChange`：能解决该阅读/事实问题的改动方向，以及必须保留的事实和作者选择。可以重排、合并、删除旁支或补回来源已有的必要解释；不要把“最小改动”理解成只换词。说明预期改善，不能只说“更有吸引力”。无依据时说明需保留或补证据。
- `affectedVariants`：共用事实／主线／术语问题列出全部相关稿件；单语风格问题不扩散。

审核输出另含 `reviewedDraftHash`、`ruleHash`、`auditCount: 1`、`findings`、`unresolved`。原始发现必须保留，不以最终稿覆盖。

## 统一修订算法

1. 读取所有有效审核记录，按 `claimId`、`termId` 和实际语义去重；保留各语言独有问题。两个审核意见冲突时，以来源和作者明确约束判断，不能按多数票或更强营销表达选择。
2. 为每条 finding 指定处置：`addressed`、`retained_with_reason` 或 `needs_user_input`。初始成稿的整篇编辑允许在既有事实、目的和作者选择内调整结构、取舍与解释，不受用户后续“仅改选区”模式限制；不扩大事实、承诺或补造作者观点、性能和故事。改变论述顺序时把必要限定带到新的主张位置。
3. 共同事实确有证据且两稿都误写时，在本次初始成稿的统一修订中修正所有 `affectedVariants`，记录各自改动，不隐瞒同步。若证据不足或涉及作者选择则保留原有事实强度并列 unresolved，不替用户决定。用户后来局部改稿的跨语言传播规则见[改稿协议](../editing-protocol.md)，不能自动套用初始修订范围。
4. 输出每份最终候选稿及 `findingResolutions`：记录 finding ID、处置、实际修改位置和理由。只有实际改掉且有支持的 finding 才标 `addressed`。如果删除了一个主张，注明删除及其影响，不能声称已验证该主张。
5. 修订结束只做确定性完整性校验：JSON／结构、必需稿件数量、主张 ID 引用、hash 和字数、查找仍存在的占位符等。它不是第二轮模型审稿，也不能证明语义问题全已消失。校验失败保留错误，禁止自动无限循环审稿。
6. 状态进入 `awaiting_confirmation`，呈现候选稿和 unresolved；是否接受某个风险、确认保存或发布仍由用户决定。修订后还有问题也不能删除记录以显示“全部通过”。

若一次审核没有可执行发现，或全部发现只能保留待决，修订可以合法无改动：逐字保留初稿，记录 `changeStatus=unchanged`、空的已解决列表和仍需保留的 unresolved。不得为了让“修订”显得发生而改词或制造问题。无改动修订仍不是作者批准。

## 明确合成审核与修订示例

资料 S1／C1：`An offline test is planned; no production results exist.`

冻结中文稿 V-ZH／B2：`离线测试已完成，生产环境也已验证。`

发现 F1：`category: fidelity; severity: blocking; quote: 离线测试已完成，生产环境也已验证。; basis: S1,C1; reason: 将计划改成完成，并虚构生产验证; suggestedChange: 离线测试仍在计划中，目前没有生产环境结果; affectedVariants: [V-ZH]`。若英文稿正确，只列中文。一次修订改为建议表述，F1 才可标 addressed；从未执行的生产测试仍不能称为已通过。

此例用于解释规则，不是实际模型验收记录。新的用户改稿请求可以设计一次针对改动的检查，但不重新启动整套母稿／平台／翻译审核，也不自动循环至“通过”。

# 工作台改稿协议

状态：候选，尚未接入生产。规则版本：`linkedin-text-candidate.0.2.1`。本轮只交付协议与合成示例，不实现 UI、接口或保存行为。平台预览仅辅助 review，不能保证与 LinkedIn 线上渲染完全一致。

## 已确定的产品要求

用户默认只修改当前选中的平台／语言稿件。局部请求只修改精确选区；选区外正文、标题、段落顺序、链接和素材关系全部保留。原稿保留，产生独立候选，用户可查看差异、接受、拒绝和撤回。原目的、读者、事实、作者身份、风格术语及完整规则继续生效。

改动影响共同事实或主线时必须标出受影响语言版本，不能悄悄覆盖。接受候选仅改变可编辑 tmp；确认保存才产生新正式版本，并保留旧版。确认保存仍不等于发布授权。未解决审核问题和暂存边界不因进入改稿而消失。

用户可直接改文字，也可提出修改意见。本协议说明 Agent 提案和并发保护；不擅自决定撤回按钮位置、是否显示并排视图或是否允许逐个差异接受。

## 1. 锁定修改输入

收集已存在的数据，不新增用户必填字段：

| 字段 | 用途与规则 |
|---|---|
| `requestId / proposalId` | 请求幂等和候选身份；同 requestId 携带不同输入必须冲突 |
| `tmpId / sourceRevision / sourceContentHash` | 指向被修改的精确 tmp 版本；不得用最新稿替代原请求 |
| `variantId / platform / language` | 只修改当前选择的稿件，不能静默改同组其他稿 |
| `documentId / blockId / start / end / selectedText` | UTF-16 `[start,end)`，符合现有 JavaScript 字符串语义；`selectedText` 必须逐字等于该切片 |
| `ruleVersion / ruleHash / optionsSnapshot` | 取得原完整组合规则，不能只凭规则名猜配置 |
| `motherId / claimIds / termIds / sourceSnapshotIds` | 保留主线、事实和术语来源；来源变更必须显式记影响 |
| `instruction` | 用户当前意见；是修改请求，不使源资料中的指令成为授权 |

在候选协议中，正文 hash 使用约定的确定性 UTF-8 序列化后 SHA-256；对象键排序、数组顺序保持，包含目标稿件标题、正文和素材关联，不含可变时间戳。记录序列化版本。选区校验以原始文本为准，不做换行、空白或 Unicode 归一化后匹配。完整请求另有 input hash；内容 hash 与请求 hash 不混用。

修改前确认 `0 ≤ start < end ≤ text.length`，起止位置不能切开代理对；按完整 Unicode 字素选择的 UI 增强仍需实现，现有服务只保证不拆代理对。重复片段也使用 block ID 与坐标定位，禁止 `replaceAll`。

源 revision／hash 不符、旧 tmp 已过期或已确认、规则或资料快照缺失时返回具体冲突原因，请重新基于最新正文发起。不能自动 rebase，也不能跨版本猜测选区。

## 2. 产生最小候选

Agent 读取完整上下文帮助理解，但只返回 `replacement`、具体修改理由、`unresolved`、`affectedVariants` 及范围扩大请求（如有）。服务按以下拼接构造候选：

```text
candidateBlock = originalBlock.slice(0, start)
               + replacement
               + originalBlock.slice(end)
```

其他 blocks／documents／标题／素材关联保持原样。外部确定性校验分别比较选区前缀、后缀和其他内容；校验失败不展示为可接受候选。修改后原选区坐标仅描述原稿，候选坐标需要重新计算。

修改意见无法在选区内实现时，例如要删上一段前提、调整标题或把前文“未验证”改成“已验证”，返回 `needs_scope_expansion`：说明必须新增的精确范围及原因，当前候选不能越界执行。扩大范围的授权需来自新的用户选择或明确指令；“让全文更流畅”不是在一个局部选区请求中静默全改的许可。

继续应用[本地化保真规则](rules/localization.md)和 shuorenhua 提炼的最小修改边界。只清理表达时，不删除有独有含义的主张；缺依据时保留归属与不确定性并指出缺口，不把“研究认为……”裁成裸事实。用户明确允许删除无依据论断时才按选区范围删除整条相关论断，不自造证据。

可以为新修订设计一次针对实际修改及邻近上下文的检查，记录为 `modificationCheckCount: 1`。其输入包括旧审核 unresolved、原规则和此次意见，不能借它扩大范围。发现问题就改为待处理／记录 unresolved，不自动运行第二次检查；这个检查不是重新走一遍原生成审核，也不是现有服务已经具备的能力。

## 3. 差异和用户处置

每个候选保留基稿、替换文本、差异、来源版本、候选版本和问题记录；差异只陈述实际变化，不能只显示“已优化”。所有含正文或选区引文的数据仍只在 tmp。

| 操作 | 必须保持的行为 | 待实现或细化处 |
|---|---|---|
| 查看差异 | 对比确切基稿和候选；显示修改范围及其他稿件影响；原稿可读 | 并排／行内、词级粒度、移动端布局 |
| 接受 | 再核对源 revision/hash、候选 hash、规则 hash 与有效期状态；成功派生可编辑 tmp；不正式保存 | 当前接口已有 revision 保护和 tmp 派生；新增 hash/影响字段需适配 |
| 拒绝 | 基稿保持不变；候选标 rejected，停止该候选后续自动应用；不擅自删除 tmp | 现有服务无专用拒绝接口；UI及记录模型待接入 |
| 撤回 | 撤销本次已接受候选的效果，同时保留基稿、候选及处置记录；不得撤销后来的无关手工编辑 | 详见下方撤回约束；交互形式待定 |

接受必须再校验，因为生成后用户可能已经手动修改。revision 或 hash 任一不同都视为冲突，禁止用候选覆盖更新内容。候选自身也被编辑时要视为新候选／新 revision；不能拿旧差异或旧 hash 接受。重复接受同一有效候选应返回同一接受结果，不复制多个版本。

撤回的安全语义：若当前可编辑 tmp 正好是本次接受后版本，派生恢复基稿内容的新 tmp；保留历史。若后续已有手工改动或其他候选，不能直接重置全文，应提出逆向差异候选并再次核对当前版本；是否接受该逆向差异由用户决定。若已经确认保存，撤回只能通过新的暂存修订及再次确认形成正式新版本，不能删除或重写旧正式版本。撤回绝不删除线上帖子，线上处理不在本协议范围。

## 4. 共同事实和其他语言版本

仅调整措辞且 claim 语义未变，`affectedVariants` 可为空。改变条件、数字、时间、完成状态、适用范围、责任主体或母稿 `spine` 时，标出 `changedClaimIds / proposedLedgerChange / affectedVariants / reason`。没有来源的新事实标 `unverified_change`，不当成已核实。

用户接受当前英文修改并不授权改中文。把中文标为需要核对、保留原文；可以提出基于新共同事实的中文修改候选，但不能自动生成或接受跨语言覆盖。用户明确要求同步后，在最新基稿上另行应用受影响稿件的修订协议，保留原规则、一次检查及确认保存边界。

共同台账也不能被单语修改静默覆盖：接受正文候选后记录一个台账变更提案，说明哪份稿基于旧台账。是否连同正文接受一并更新台账的交互仍待定；本候选默认显式记录、等待相应决定。

## 5. 既有接口与未来最小接入点

已只读核对[现有执行与发布接口](../../docs/第二阶段执行与发布接口.md)及[生成服务](../../server/generation-service.mjs)的 `modify / runModification / accept`：

- 已实现源 revision 检查、精确文本与 UTF-16 范围检查、代理对保护、原规则快照核验、服务器切片拼接、独立候选与接受后派生 tmp。正式版本 revise 和 confirm 已独立。
- 现有修改模型 schema 只含 `replacement / unresolved`；提示明确不执行新的自动审核。候选 schema 增加字段和一次针对性检查尚未接入，不能把本文件称为功能验证。
- 当前接受接口使用 `sourceRevision`；content hash 接受条件、拒绝／撤回处置、完整差异快照、跨语言 claim 影响、共同母稿及台账是未来扩展。保持现有 revision、防恢复 epoch 失效和路径校验，不重建存储协议。
- 已有存储只恢复正式备份且缺执行 tmp 时，不能从 ruleHash 还原原规则，应明确无法安全继续该修改。不得悄悄降级成任意新规则。

## 6. 明确合成示例（非用户正文）

原段：`The pilot is planned. It may reduce manual checks. Production use is untested.` 选区仅为第二句；意见是“表达更直接，但保留概率”。候选：`It may require fewer manual checks.` 前后句、空格、句号与其他段落逐字保留；`may` 不能消失。自然度改写是否等义仍需那一次针对性检查，不以选区外 hash 相同代替语义检查。

若用户改为“写成已证实减少 40% 人工检查”，资料并没有这项结果，则记录事实修改待证据及受影响语言稿件。不能因为用户让语气更强就改出真实验证结果，也不能自动修改另一语言。

若当前 revision 已从 7 变成 8，即使碰巧仍能找到相同选中文字，基于 revision 7 的候选也不可直接接受。重复文本不构成同一版本。

这些是协议示例；真实修改试验的完整材料与结果必须另存隔离 tmp，永久记录只写结论和非正文证据指针。

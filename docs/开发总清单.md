## 5. 双平台共同内容与技能深化

当前 LinkedIn 和 X **各自有平台内的双语共同母稿**，混选时按平台分流，各跑一份母稿。事实变更提示／显式同步限制在同平台另一语言，避免跨平台误覆盖。目标“一份资料→一份共同母稿→多个平台改写→本地化→每稿一次审核／修订”仍是待做的整体整合，不能靠把两条流程串在一起宣称完成。

| SKILL-01／P1 | 从已归档候选实读、去重、逐条取舍，核查原作者版本／许可／依赖。依赖[候选清单](技能候选与取舍清单.md)和[资料库](../skill-library/README.md) | “来源条款→保留／改写／舍弃→理由→适用平台／阶段”矩阵 | 不把下载、收藏或 Hub 描述当采用；剔除编造数据、强制 CTA、固定删字比例、过时平台规则及不合用脚本；保留未确认项 | 引用和改写许可不清楚时不整包复制；候选搜集不等于安装／运行授权 |
| SKILL-02／P1 | 将 SKILL-01 的有效增量接入母稿、平台风格、视觉 brief、本地化、审核的固定映射；保留当前规则版本 | 小而明确的新规则版本、选项映射、来源说明与回退边界 | 用户仍只选创作选项；每稿得到唯一完整规则；不引入二次自动文字审核、不把团队 skill 原多 Agent 轮次直接搬进来 | 跨平台规则依赖 CORE-01；单平台小增量可独立评审；图片 runner 与配图风格规则分开 |
| QUALITY-01／P1 | 建立跨材料／目的的留出试稿与编辑评估，依赖已批准的调用范围；先形成不调用模型的样例／评价契约 | 对照样例、事实／表达／双语／图片评估及失败复现 | 自然生成错误能被发现；无问题允许不改；事实条件不漂移；对齐用户 launch-kit／launch-copy 质量目标而不硬编码产品标准答案；延迟和失败率按实际样本报告 | 真实调用另按范围执行；用户最终质量判断不可用模型分数替代 |

技能资料整理后的下一步是 **SKILL-01 取舍→SKILL-02 小范围接入→QUALITY-01 对照验证**，不是再次把所有 skill 无差别安装，也不是立刻重写现有 LinkedIn／X 规则。优先关注跨平台改写、事实一致性、视觉 brief、自然表达及本地化的实际增量。

## 6. 后续平台、内容形式与运行维护

下列保留完整项目范围，不是当前 LinkedIn MVP 的验收门槛。每个平台先把内容对象、规则和可用发布方式分清；支持生成、能整理发布包、API 可调用、真实发帖成功是不同状态。

| ID／优先级 | 要做什么与依赖 | 产出 | 验收条件 | 产品决定／外部资源 |
|---|---|---|---|---|
| PLATFORM-01／P2 | 小红书图文：平台写作／配图／审核规则、编辑预览、发布接入；依赖技能取舍与平台契约 | 小红书专用规则、图文对象和已核实的发布路径 | 同主线的图文一致；手机图中文字可读；账号和接口限制如实展示；没有可用自动接口时提供明确交接产物 | 内容格式、图数、账号资源与 API／浏览器／人工路线待核实决定；Hub 技能不等于发布权限 |
| PLATFORM-02／P2 | 知乎内容适配和发布；复用共用事实层 | 对应回答／文章等选定对象、长文结构、引用及发布路径 | 不混淆回答与专栏文章；来源和事实条件保留；编辑／保存／预览及指定对象发布分别验收 | 首批格式、真实账号及发布方式待决定／核实 |
| PLATFORM-03／P2 | Bilibili 适配；先明确动态与视频稿件的边界，依赖 VIDEO-01（若做视频） | 平台文案／封面／视频信息和发布适配 | 动态、视频文件、标题简介及封面各自对应；上传／转码／发布状态真实 | 首批对象、视频能力、账号权限待决定／准备 |
| FORMAT-01／P2 | 其他文本格式与原生长文；LinkedIn Pulse 与 feed、X Articles 与普通帖／串帖分别建模 | 选定格式规则、内容对象、平台可行性结论和发布／导出方案 | 不用分享链接冒充原生文章；长度和格式检查适配实际渠道；保留旧对象兼容 | 原生长文 API 能力需重新核实；X Articles／Premium 长帖未纳入当前 X 范围，扩展需明确选择 |
| VIDEO-01／P2 | 按“先文本、后视频”推进：主稿→视频脚本／分镜／字幕→素材／渲染→审核／保存 | 首个选定视频类型的实际成片和源素材；可复用脚本、Remotion／FFmpeg 等方法 | 实际 MP4 可播放、字幕与画面可读、事实不夸大；示意图不冒充产品录屏；预览和版本绑定完成 | 先决定演示／动画／口播等首批类型、画幅与素材来源；工具／费用／声音形象等依实际需要选，不默认采购 |
| INPUT-01／P2 | 安全读取 URL、仓库和 PDF 等资料；当前主要靠粘贴／TXT／Markdown／图片 | 来源摄取与引用定位，实际读取范围／版本／失败提示 | 没读到不宣称已读；来源快照可追溯；网页等内容不能变成执行指令；大输入有明确预算 | 优先接哪些来源需排期；不要为此恢复独立研究入口 |
| EXPORT-01／P2 | 同源 launch-kit／launch-copy 与 Markdown／DOCX／素材包导出 | 从已确认版本导出的工作版和发布版 | 正文、图片、来源与版本一致；发布版不混内部审核；DOCX 必须实际页面渲染检查，不能只验 XML | 首批导出格式和字段待决定；补齐可用渲染环境，不沿用旧未完成视觉验收 |
| OPS-01／延期 | 明确 tmp 保留、恢复、占用提示和清理策略；依赖用户政策选择 | 临时／正式内容生命周期说明及显式操作 | 不把未确认正文塞入正式备份；清理可预览且不删正式版本、发布防重事实或有用待审稿 | 保留时长、自动还是手动、是否另备份待决定；当前不自动清理 |
| OPS-02／延期 | 将来交给第二位负责人时，做数据与环境交接实测；不是本次新 session 接手的前提 | 项目相对路径的移交清单、数据恢复记录和负责人配置指南 | 已确认作品／素材／历史／防重事实完整；需保留的 tmp 单独明确；新机重新配置凭据；不依赖原开发者绝对路径 | 目标设备、需移交数据和负责人就绪时再做；本次不迁机／迁服务器 |
| OPS-03／延期 | 其他人只读查看工作台及访问控制 | 经确认的只读入口、身份／权限／公开范围设计 | 未授权者不能读私稿；只读者不能生成、改稿、保存或发布；不暴露密钥和整个本机服务 | 访问人数、网络范围、认证、部署位置待决定；当前保持 `127.0.0.1` |
| OPS-04／延期 | 在有实际需要时增加 Claude 或其他执行适配，保留现有统一任务保护 | 明确供应商契约、能力状态和独立验收 | 同样遵守 tmp、取消、超时、事实规则和真实完成证据；不为抽象而重建通用 Agent 平台 | 有新供应商／账号／成本需求再决定；Codex 不是永久唯一供应商承诺 |
| FEEDBACK-01／延期 | 反馈分析继续留空，未来重新设计 | 之后批准的数据对象、权限及分析目标 | 指标、评论等必须有实际来源；未知不填 0；当前不纳入 MVP 验收 | 尚未设计，不能从历史研究清单恢复采集或分析开发 |

## 7. 可并行范围与共享文件 owner

一个整合 owner 负责公共接口、共享文件冲突、构建与最终验收；工作包可以由同一 session 的 subagent 执行，也可在明确分支中推进。各包先约定输入输出，不以“各自把共享文件改完”代替整合。

| 工作包 | 可独立推进的工作 | 先后依赖／共享 owner |
|---|---|---|
| 验证与外部资源 | MVP-01 的隔离测试稳定性；MVP-03 与 X-01 的配置清单／账号资源准备；MVP-05 的验收用例 | 真实账号动作由负责人执行；发布适配修改与整合 owner 对齐；MVP-04／X-02 等待资源和具体确认 |
| 产品体验 | UX-01／02 可先做只读展示设计；UX-06 准备文案；UX-07 用例已入仓，实施后执行 | `src/ContentWorkspace.tsx`、共享类型、样式、词典及路由由 UI owner 汇总；实际接入先有 UX-03／CORE-01 契约；UX-04／05／06 基础能力必须进入体验验收 |
| 任务与共同母稿 | CORE-01 契约、UX-03 的输入快照与阶段控制共同设计 | `server/generation-service.mjs`、`generation-http.mjs`、`text-pipeline.mjs`、`src/content-types.ts` 由执行整合 owner 统一；CORE-02 和恢复实现不能盲目同时改同一状态机 |
| 技能与质量 | SKILL-01 来源分析和 QUALITY-01 样例／评价契约可与 UI、外部资源并行；各平台官方资料核查可独立 | SKILL-02 在规则 owner 接受取舍后落地；`rules/text/`、`rules/x*/` 的版本、映射及调用载荷由规则／执行 owner 联合验收 |
| 图片与发布 | 平台图片规则分析、LinkedIn 指定稿质量续验、X 外部配置各自独立 | 共享 `image-runner.mjs`／worker 只由图片 owner 修改；LinkedIn 和 X 的对象绑定分别保留；`content-store.mjs`、备份协议、HTTP 路由由整合 owner 审阅 |
| 文档与扩展准备 | 后续平台、视频、导出、只读访问可先写范围与可行性，不必等待当前真实发布 | 未决定的范围先形成产品选择，不开始未授权实现；不要抢占当前闭环资源 |

建议接续顺序：核对当前基线与权限范围 → MVP-01 与已授权的独立准备并行 → 完成 LinkedIn 指定稿图片和外部闭环 → 自动及用户验收。同时可以推进技能增量分析与体验设计；UX-03／CORE-01 先共同完成实际接口契约，再分包实施 UX-01～06，最后执行 UX-07。CORE-02 可后续，不阻止先完成已有双平台的任务体验；单母稿能力必须另有证据。X 的真实创作／图片不从零重做，重点转向外部授权发布及双平台一致性。

每个工作包收尾都需注明：代码完成、自动测试、浏览器验证、真实模型／图片、真实平台动作分别通过了什么；同步[会话交接](SESSION_HANDOFF.md)和对应验证记录。未完成项继续留在本表，不能用测试数量、说明卡片或技能名称代替用户可用能力。

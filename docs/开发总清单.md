## 1. 范围与优先级

- **本次只整理文档和skill资料。** 用户整理完成后另授权将本轮成果commit／push；这不自动授权执行下列开发、真实调用、探测、重启、确认保存、上传媒体或发帖，也不授权后续任务自行提交。接手时依据用户给该任务的最新明确范围执行，不因列表写“P0”就自行开始。
- **P0 闭环**：当前 LinkedIn 图文 MVP 的外部与最终验收缺口，以及整合交付基线。**P0 体验**：已记录的首批易用性改造，属于独立开发包，不以此否认现有文本能力。**P1**：双平台产品一致性、X 外部闭环及质量完善。**P2**：后续扩展。**延期**：先保留，条件或产品决定具备后再启动。
- “可并行”表示依赖允许，并非授予实施权限。所有任务均保留三项必填、固定规则映射、每稿一次审核、tmp、显式保存／发布、版本并发、防重及旧数据兼容要求。
- LinkedIn 原验收的网络诊断、能力探测、真实重试和会触发探测的服务重启仍按用户决定暂缓。9 月 26 日 X 在其独立授权任务中已完成真实文字和图片验证；这既不是“所有 Codex 能力仍不可用”，也不意味着 LinkedIn 的指定稿件、图片质量、双语绑定及原服务已验收，不能据此自动恢复原任务。

## 5. 双平台共同内容与技能深化

当前 LinkedIn 和 X **各自有平台内的双语共同母稿**，混选时按平台分流，各跑一份母稿。事实变更提示／显式同步限制在同平台另一语言，避免跨平台误覆盖。目标“一份资料→一份共同母稿→多个平台改写→本地化→每稿一次审核／修订”仍是待做的整体整合，不能靠把两条流程串在一起宣称完成。

| ID／优先级 | 要做什么与依赖 | 产出 | 验收条件 | 产品决定／外部资源 |
|---|---|---|---|---|
| CORE-01／P1 | 定义真正跨 LinkedIn／X 的 intake、母稿、事实／术语账本及平台子任务契约；依赖当前两套真实接口 | 输入／工件／版本关系、平台分支预算、失败隔离和迁移说明 | 平台×语言才增加稿件；格式多选仍为同稿内容对象；母稿不受目标语言顺序污染；旧任务可读／可改边界清楚 | 核心方向已确认；契约是实现设计，不新增必填项；与 UX-03 共享任务模型须统一 owner |
| CORE-02／P1 | 依 CORE-01 接入单母稿多平台分支、跨平台事实影响提示及显式派生修订 | 共用母稿执行、平台适配、各自审核、版本追踪 | 混选时只生成一份母稿；某平台失败不丢另一平台成果；跨语言／跨平台不静默覆盖；取消、恢复、发布版本防重不退化 | 跨平台事实修改如何提示／局部同步的交互需明确；新修订需要的审核不能拿旧审核替代 |
| SKILL-01／P1 | 从已归档候选实读、去重、逐条取舍，核查原作者版本／许可／依赖。依赖[候选清单](技能候选与取舍清单.md)和[资料库](../skill-library/README.md) | “来源条款→保留／改写／舍弃→理由→适用平台／阶段”矩阵 | 不把下载、收藏或 Hub 描述当采用；剔除编造数据、强制 CTA、固定删字比例、过时平台规则及不合用脚本；保留未确认项 | 引用和改写许可不清楚时不整包复制；候选搜集不等于安装／运行授权 |
| SKILL-02／P1 | 将 SKILL-01 的有效增量接入母稿、平台风格、视觉 brief、本地化、审核的固定映射；保留当前规则版本 | 小而明确的新规则版本、选项映射、来源说明与回退边界 | 用户仍只选创作选项；每稿得到唯一完整规则；不引入二次自动文字审核、不把团队 skill 原多 Agent 轮次直接搬进来 | 跨平台规则依赖 CORE-01；单平台小增量可独立评审；图片 runner 与配图风格规则分开 |
| QUALITY-01／P1 | 建立跨材料／目的的留出试稿与编辑评估，依赖已批准的调用范围；先形成不调用模型的样例／评价契约 | 对照样例、事实／表达／双语／图片评估及失败复现 | 自然生成错误能被发现；无问题允许不改；事实条件不漂移；对齐用户 launch-kit／launch-copy 质量目标而不硬编码产品标准答案；延迟和失败率按实际样本报告 | 真实调用另按范围执行；用户最终质量判断不可用模型分数替代 |

技能资料整理后的下一步是 **SKILL-01 取舍→SKILL-02 小范围接入→QUALITY-01 对照验证**，不是再次把所有 skill 无差别安装，也不是立刻重写现有 LinkedIn／X 规则。优先关注跨平台改写、事实一致性、视觉 brief、自然表达及本地化的实际增量。

## 7. 可并行范围与共享文件 owner

一个整合 owner 负责公共接口、共享文件冲突、构建与最终验收；工作包可以由同一 session 的 subagent 执行，也可在明确分支中推进。各包先约定输入输出，不以“各自把共享文件改完”代替整合。

| 工作包 | 可独立推进的工作 | 先后依赖／共享 owner |
|---|---|---|
| 验证与外部资源 | MVP-01 的隔离测试稳定性；MVP-03 与 X-01 的配置清单／账号资源准备；MVP-05 的验收用例 | 真实账号动作由负责人执行；发布适配修改与整合 owner 对齐；MVP-04／X-02 等待资源和具体确认 |
| 产品体验 | UX-01／02 可先做只读数据展示设计；UX-06 可准备文案和导航方案 | `src/ContentWorkspace.tsx`、共享类型、样式、词典及路由由 UI owner 汇总；UX-03／05 与 CORE-01 先统一任务契约 |
| 任务与共同母稿 | CORE-01 契约、UX-03 的输入快照与阶段控制共同设计 | `server/generation-service.mjs`、`generation-http.mjs`、`text-pipeline.mjs`、`src/content-types.ts` 由执行整合 owner 统一；CORE-02 和恢复实现不能盲目同时改同一状态机 |
| 技能与质量 | SKILL-01 来源分析和 QUALITY-01 样例／评价契约可与 UI、外部资源并行；各平台官方资料核查可独立 | SKILL-02 在规则 owner 接受取舍后落地；`rules/text/`、`rules/x*/` 的版本、映射及调用载荷由规则／执行 owner 联合验收 |
| 图片与发布 | 平台图片规则分析、LinkedIn 指定稿质量续验、X 外部配置各自独立 | 共享 `image-runner.mjs`／worker 只由图片 owner 修改；LinkedIn 和 X 的对象绑定分别保留；`content-store.mjs`、备份协议、HTTP 路由由整合 owner 审阅 |
| 文档与扩展准备 | 后续平台、视频、导出、只读访问可先写范围与可行性，不必等待当前真实发布 | 未决定的范围先形成产品选择，不开始未授权实现；不要抢占当前闭环资源 |

建议接续顺序：核对当前基线与权限范围 → MVP-01 与已授权的独立准备并行 → 完成 LinkedIn 指定稿图片和外部闭环 → 自动及用户验收。同时可以推进技能增量分析与体验设计；UX-03／CORE-01 先共同定契约，再分包实施。X 的真实创作／图片不从零重做，重点转向外部授权发布及双平台一致性。

每个工作包收尾都需注明：代码完成、自动测试、浏览器验证、真实模型／图片、真实平台动作分别通过了什么；同步[会话交接](SESSION_HANDOFF.md)和对应验证记录。未完成项继续留在本表，不能用测试数量、说明卡片或技能名称代替用户可用能力。

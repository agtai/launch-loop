## 一次内容工作的完整链路

1. **研究**：读取 README、功能文档、基准、版本记录及已发布内容，形成有来源和核查时间的产品事实。把作者的表达要求与事实证据分开记录。
2. **生成**：从同一份简报生成中文、英文文章和所选渠道版本；两个语言版本分别编辑，不要求逐字翻译。
3. **审查与迭代**：用户查看排版后的文章，按段修改或提交意见；Agent 按 skill 修订。事实核查、语言检查、渠道格式检查分别给出结果。保留上一版和修改记录。
4. **发布**：把指定语言、渠道与已批准版本绑定，展示最终预览，通过该渠道实际可用的接口或浏览器流程提交，记录真实文章/帖子链接和执行状态。
5. **反馈**：按发布记录收集可获取的指标与评论，显示采集时间及缺失项目；提取疑问、需求、故障、试用意向和下一轮选题。

## 两种交付物

**Launch kit 工作版**：含内容目录、受众和角度、双语正文、各渠道衍生稿、封面/配图、事实来源、审查问题、修改意见、发布说明与计划。它是用户迭代的主要材料。

**Launch copy 发布版**：从同一内容记录输出已经确认的版本，图片在前，每条内容有清楚标题，正文可直接复制；依项目 skill，仅保留必要的简短 Posting 提示。不得把内部审查记录混入公开正文。

两个文件应由同一份结构化内容产生，避免修订时只更新其中一份。中英文可以各自导出，也可以导出双语合订版本。DOCX 是正式交付格式之一；工作台页面须同时提供舒适的阅读与编辑体验。

## 内容编辑界面

- 主入口展示内容项目及状态，打开后直接阅读文章。
- 左侧为文章/渠道目录，中间为有标题层级、段落、列表、图片与链接的正文，右侧为意见、事实依据与修订记录。
- 提供中文/英文切换，以及工作版/发布版预览。
- 可以修改标题、分段正文、图片说明和渠道提示；支持局部修订，保留未选中的段落。
- 清楚显示当前版本、是否有未保存修改、审查结果，以及具体批准了哪个版本。
- 编辑已批准正文会产生新版本，需要重新确认该版本后才能发布。
- 可导出 DOCX、Markdown 和发布所需的素材；原文和导出结果须一致。
- “生成”“修订”“发布”“采集反馈”必须显示真实执行状态、失败原因与产出。未配置执行工具时不能用模拟成功状态代替。

## s1a-launch-kit 的复用方式

| 现有内容 | 如何复用 | 需要调整的地方 |
|---|---|---|
| 固定标题、核心信息、术语 | 保存为项目写作规则，由生成和审查共同读取 | 明确规则版本；改变固定标题时遵循作者要求 |
| README、基准、skills、版本记录核验 | 复用为写作前资料检查 | 每次重新核查；旧性能数字、日期和命令不能当作当前事实 |
| LinkedIn article + feed post 等渠道结构 | 复用为内容类型模板 | 第一轮优先 LinkedIn；渠道按需要启用，不必每轮生成全部渠道 |
| 中英稿 | 共享事实，按目标读者分别表达 | 现有 skill 主要围绕英文发布；双语对照和术语一致性须补为明确要求 |
| 完整 kit 与纯文案 Word 交付 | 复用为双导出视图 | 共用内容数据；导出后检查实际排版 |
| ai-rhetoric-lint | 有工具时保存检查结果和作者保留项 | 尚未确认该依赖在本机可运行，不得在未运行时标记 linted |
| 分渠道字数检查 | 复用为可执行验证器 | 限制来自当前平台和发布工具，不能永远硬编码历史数值 |
| 排期、联系媒体和社区 | 复用其任务分类与交付格式 | 日期、接收人、账号与最终正文另行明确；参考文件不自动授权发信或发帖 |

用户已确认：Claude／Codex 都可以，优先复用现有账号。执行层先对接实际可用的现有 Agent 入口；不要把页面框架绑定到单一模型提供商，也不要预设必须新买服务或 API。账号可用性、具体执行入口和权限仍需在接入时验证。无需为了界面先重建一套通用 Agent 平台。

## 发布与反馈必须区分的对象

LinkedIn 原生长文章与 LinkedIn feed post 是两种产出。把一个文章链接分享到动态，不等于创建 LinkedIn 原生长文章。渠道适配器必须声明它支持哪一种操作，不能仅因某工具写着支持 LinkedIn 就认为支持全部文章功能。

反馈按文章或帖子分别记录。阅读数、曝光、点击、点赞、评论、转发和 GitHub 变化不混用；无法取得的数据标记为未获取，不能填 0。公开可见评论与只有作者能查看的统计权限分开处理。

本次官方资料核查发现：

- LinkedIn [Posts API](https://learn.microsoft.com/en-us/linkedin/marketing/community-management/shares/posts-api?view=li-lms-2026-09) 的 article 是附带 source URL 的链接卡片。本次未找到可依赖的公开 Pulse 长文章正文创建 API；[原生文章编辑器](https://www.linkedin.com/help/linkedin/answer/a521657) 是已确认的长文入口。
- Buffer 可以复用动态发布；[官方 API 说明](https://support.buffer.com/en-us/articles/what-is-buffers-api-GtIYIQilz5) 把指标能力列为实验功能，公共 API 暂不支持评论读取/回复。
- [Typefully 分析说明](https://support.typefully.com/en/articles/8718148-analytics-page-metrics) 当前仅支持 X，不能把它当成现成的 LinkedIn 反馈统计来源。
- LinkedIn 个人指标和评论读取各有权限条件，和普通发布授权分开。第一版应有原生导出/导入的可用后备路径。

完整接入核查另见 [LinkedIn发布与反馈接入核查.md](LinkedIn发布与反馈接入核查.md)。

首篇文章已出现可用的真实反馈样例：读者询问 builder 的适用边界判断，是只依靠初始手写样例，还是会在运行过程中调整；同时关注低置信度交回 System 2。可归类为“技术疑问／后续解释选题”。来源为上述公开文章评论区；这不是完整评论采集或传播统计，也不据此推断总体读者态度。

内容记录至少关联：项目、语言、渠道/内容类型、标题和正文、素材、事实来源、skill 版本、生成执行记录、修订版本、审查结果、批准版本、发布链接及反馈采集时间。

## 第一轮验收

以现有 system1-agents 材料为输入，生成一组中英文文章和配套 LinkedIn 动态稿；用户能在页面按段修改，Agent 能按意见修订；能导出可阅读、可复制的 kit 和 copy；发布状态必须关联真实渠道结果；至少一次反馈采集能够保留原始来源，并形成具体行动或后续选题。

首轮发布使用何种账号连接与原生文章提交方式，需要按实际可用能力落实。不得把已有文章重新发布当作系统测试。

## 当前工作台与目标的差距

已经具备：本地运行、方法库、调研、任务分工、记录、资料检索、备份与交接。

仍需实现：内容正文与版本存储、双语阅读编辑界面、真实 Agent 执行接入、内容包与 DOCX 导出、发布适配、反馈采集及对应执行记录。这些是下一阶段的主体工作，不能只通过增加说明卡片来替代。

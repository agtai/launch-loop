# 任务交互与恢复规范

更新：2026-09-26。状态：**后续实现的行为要求；本轮仅补充文档，未实现或验收这些新增能力。** 用户已要求补齐 Easy、Hands-off、Transparent、Intervene at any point 的设计、开发依赖与验收，并 commit／push。

本规范承接[开发总清单](开发总清单.md)的 UX-01～06、CORE-01～02，验收见[四项目标体验验收](四项目标体验验收.md)。现有行为以[LinkedIn 接口](MVP执行与素材接口.md)、[X 接口](x/implementation.md)及 main 实际代码为准。本文不把目标状态名当作已经存在的 API／数据库字段。

## 1. 交付目标与边界

- **Easy**：直接三项必填开始；当前成果、待处理问题和下一步优先展示。平台、语言、格式、图片策略有可见摘要，高级配置按需展开。待适配平台不可误选；首次环境配置与日常操作分开说明。
- **Hands-off**：一次启动后自动完成所选正常链路，达到可审阅成果或具体待决事项；不要求操作者逐阶段点击。异常时保留有效产物，给出可执行的后续动作。
- **Transparent**：展示来源、固定规则、阶段结果、审核发现与修订处置，绑定实际版本。展示执行证据和简明解释，不展示私有思维链，不让用户选择 skill。
- **Intervene**：用户运行中可以提出暂停、补资料、改方向，并得到确定反馈；安全退出后按影响范围继续。不能宣称暂停模型内部状态，也不能承诺撤销已经提交的平台动作。

只有平台 × 语言分别出稿；X 普通帖和串帖仍为同语言包中的内容对象。三项必填、固定规则、每稿一次审核、tmp、显式保存与独立发布确认不变。不新增研究／独立审查入口，不实施反馈或其他平台。技能深化可以并行，不能替代任务控制与界面实现。

功能 MVP、四项体验目标和真实外部发布分别留证。MVP-05 通过不自动满足本规范；本文写完也不代表 UX／CORE 任务完成。

## 2. 同一任务的身份与数据关系

以下是需要由 UX-03／CORE-01 共同落实的语义；实现前须写清与现有 job、tmp、ContentVersion 的字段映射，不能直接重建数据库或批量改旧记录。

| 对象 | 稳定关系与用途 |
|---|---|
| 内容任务 | 同一创作目标的入口，关联平台／语言成果、图片、历史尝试和正式版本；任务编号不因某次失败变化。不增加用户创建项目的步骤 |
| 输入快照 | 固定本次资料字节／hash、实际读取范围、目的、读者、选项、用户图及规则版本。继续任务读取此快照，不读取另一份左侧表单 |
| 任务修订 | 用户调整输入或正文后产生，记录父修订及变更范围；旧稿仍可查。主视图明确当前选中修订，不以时间最新的一条日志决定当前稿 |
| 执行尝试 | 一次显式开始／继续的执行，关联输入快照、阶段预算、取消／恢复边界和错误；重试不能抹掉之前失败或刷新已有续接限额 |
| 平台／语言包与内容对象 | 保留平台、语言、document 和 X 逐帖稳定 ID；每个对象可分别显示正文和图片状态。某个分支失败不丢其他分支成果 |
| 阶段工件 | 带来源、父工件、规则、正文 hash／revision 和执行归属；只有依赖仍有效才允许复用。不能仅凭规则 hash 从其他任务取账本 |
| 正式版本／发布尝试 | 正式版本由用户确认产生、不可变；发布另绑定账号、正式版本、对象、正文和图片。任务变化不改变已有正式版本或已发事实 |

未确认正文、完整输入、审核、图片和过程输出继续只在所用 dataDir 的 tmp；新增任务索引不得把这些正文副本写入正式日志或备份。tmp 缺失／旧恢复 epoch 的任务只能按实际证据降级，不凭 hash 伪造工件。

页面至少独立显示：正文是否可审阅、图片是否就绪、是否有待处理问题、是否正式保存、是否发布。不能用一个“失败”覆盖“中文已完成、英文待处理、图片失败”的组合。

## 3. 状态、主操作与用户反馈

状态是面向用户的语义，实际接口映射由实现契约固定。主操作依据当前选中的任务／对象；其他有效操作仍可见，不能因主操作排序隐藏正文。

| 状态／组合 | 页面必须表达 | 可执行动作与边界 |
|---|---|---|
| 待开始／已排队 | 本次输入与配置摘要、尚未产出 | 开始前可调整；取消排队不触发模型 |
| 运行中 | 实际阶段、已完成产物、开始时间与阶段预算；不编造完成百分比 | 查看已完成稿；暂停并调整；取消。左侧另填内容不偷偷改变当前任务 |
| 请求暂停／正在退出 | 已收到请求、阻止新阶段、当前调用退出状态 | 查看成果；不显示“已暂停”或允许新尝试接管，直到安全边界得到确认 |
| 已暂停 | 有效产物、未完成阶段、原始输入和调整入口 | 补资料／改方向／编辑已完成稿；查看影响范围后明确继续，或结束执行 |
| 缺证据／要求冲突 | 哪条主张缺哪份依据，或哪两项要求冲突；受影响范围 | 在任务内补充／澄清，再查看恢复计划；不自行编造事实或改变用户目的 |
| 部分完成／某阶段失败 | 可审阅正文保留；各失败原因、关联尝试及恢复资格分别可查 | 查看正文；对相关阶段继续、重试、替换图片或显式选纯文字；不能自动降低图片要求 |
| 服务中断／退出未确认 | 最后可信阶段、是否还有未确认调用、为何暂不能续接 | 核对执行状态；安全边界恢复后显式继续。刷新、重开页面和重启均不自动调用模型 |
| 可审阅 | 当前终稿、图片结果、审核与修改依据；尚未确认保存 | 改稿、检查差异、确认保存。必要图片／正文校验不通过时说明原因 |
| 已保存／待发布 | 精确正式版本、对象和素材；保存不等于发布 | 用此版本准备发布，进入独立账号／版本预览和确认 |
| 发布中／部分已发／结果未知 | 已提交对象、平台已知结果与尚不确定部分 | 查看／核对结果；仅明确可继续状态按发布器规则再次确认；unknown 禁止自动重发 |
| 已取消 | 本次执行已结束、已完成成果仍可查、取消作用范围 | 查看／派生新尝试；不能把取消当作自动恢复或删除旧数据 |

主操作优先解决影响当前动作的阻塞：发布 unknown 的核对提示不得被“重试”取代；退出未确认先处理执行状态；缺资料／冲突先补充；正文可审阅时始终提供看稿入口。历史失败默认折叠，但失败原因和次数不能隐藏。

## 4. 暂停、调整、继续的控制协议

1. **请求有范围。** 任务级“暂停并调整”默认阻止该任务所有未开始阶段与自动配图调度；对象级图片取消只影响所选对象。界面明确两者，不能把一个对象的取消显示成整个任务已停止。
2. **先设写入屏障。** 服务端确认请求时校验任务修订／执行身份，记录控制状态，阻止后续调度和旧尝试写入当前修订。界面等待服务端确认，不乐观显示“已暂停”。
3. **退出有界。** 使用现有 runner 取消／退出机制和该阶段预算；接口契约必须记录实际适用的退出期限、清理办法及超时映射。未确认退出时显示具体阻塞，不无期限转圈、不虚报退出，也不启动与其冲突的新调用。仅处置本项目对应进程，不批量杀 Node。
4. **只使用完整可信工件。** 中断的半份模型输出不成为可复用稿；安全暂停可以保留已完整通过校验的上游。晚到结果即使完成也不能附入已替换修订。
5. **调整产生新修订。** 输入或用户正文变化记录父关系、变更范围；展示将保留／重新执行／需确认同步的清单及原因。目的或共同事实变化通常影响更广，不能承诺所有修改都只重跑一个阶段。
6. **继续是一次明确动作。** 以任务 ID、期望修订、固定快照、恢复计划及幂等请求身份提交；再次核对来源／规则／父链／正文／恢复 epoch。计划已过期则返回冲突并重新展示，不按旧计划执行。重复点击、并发标签页只形成一个有效尝试。
7. **边界持久。** 刷新或服务重启后仍保留暂停、取消、已用续接次数和失败记录；中断不自动恢复。新尝试不能重新消费另一尝试的授权或解除发布防重。

暂停与取消分开：暂停为在同任务调整后继续；取消结束当前执行，后续若派生新尝试必须显式发起。查看任务、查看依据、切换界面语言、打开发布预览不隐式触发创作、正式保存或发布。

## 5. 修改影响与复用矩阵

“失效”表示不能作为新修订的有效依据，旧产物与历史仍保留。未受影响分支须验证依赖关系后复用；范围无法可靠确定时采用保守失效并说明原因，不让模型的自评直接证明安全。

| 用户变更 | 可以保留 | 必须重新处理／明确提示 |
|---|---|---|
| 无输入变化，继续符合条件的失败阶段 | 已完整且校验通过的来源、母稿、平台稿及成功冻结审核 | 仅执行缺失且允许续接的阶段。现有 LinkedIn 两类一次续接限制继续有效；没有资格时明确说明并允许带原资料新建尝试 |
| 修改写作目的／目标读者／主线，或全局作者／风格要求 | 历史全部保留；未变化的来源字节可复用 | 新输入快照，重新形成母稿及受影响平台／语言下游；受影响审核与图文绑定不能沿用 |
| 补充或修正事实、证据、时间／版本信息 | 无依赖关系的产物，且需有可核对依据 | 更新事实账本并列出受影响主张与分支；重新处理相关上游和下游。当前依赖不足时保守扩大范围。已被用户编辑的其他稿只提示并提供显式派生／同步，不静默覆盖 |
| 只修改某平台的表达／格式要求 | 母稿及其他平台，前提是共同事实和全局要求未变 | 该平台改写、受影响语言包及其审核／修订；相关图片重新核对绑定。X 包内普通帖／串帖维持同包一次审核，不按子帖增加审核 |
| 只添加一种目标语言／一个平台 | 现有未变化稿、通过的审核及符合依赖的上游 | 生成新增分支；不因列表顺序改变母稿语言。跨平台共用母稿须待 CORE-02 实现；此前不把双流水线包装成单母稿 |
| 手动编辑正文或接受局改提案 | 原稿、选区外内容及其他对象／语言 | 新 tmp 修订；旧审核不能直接为新编辑背书，旧图片绑定按正文依赖失效。共同事实变化提示其他稿影响，同步必须显式选择 |
| 仅调整图片要求／替换素材／选择纯文字 | 未依赖该图片作证据的正文和文字审核 | 仅处理所选对象图片与绑定；纯文字是显式选择，旧图迟到不能挂回。若图片本身是创作事实来源，则按补充事实一行处理 |
| 只切换界面语言／调整页面展示 | 全部内容和执行工件 | 无生成／审核／保存／发布动作；不翻译用户正文或来源 |
| 运行期间可用规则版本升级 | 原任务已经固定的规则与适用工件 | 不自动换规则；只有显式采用新规则的尝试才重算受影响阶段，用户仍无需手选 skill |

审核复用按**同一平台／语言包、冻结正文、来源、规则及父链**判断，不只比正文。成功审核在该冻结上下文只执行一次；失败且没有有效结果的调用不冒充成功审核。更改输入产生新的冻结稿时，只对受影响的新稿按原链路审核一次，不追加第二轮自动内容审核。

审核后按该报告产生的修订终稿，可以通过冻结稿→审核→修订的完整关系展示依据；不能因修订正文 hash 不同就再审一次。用户之后直接编辑时标明“原审核对应旧稿”；手动修改本身不偷偷触发模型。用户明确继续创作／同步所生成的新候选按其新冻结上下文处理。正式保存校验沿用现有事实、版本、素材约束，不借本文擅自增加每次手改强制调用模型的门槛。

旧图字节允许在新正文上显式重新检查并形成新绑定；不必无条件重画。检查失败不能静默改为生成或纯文字。X 的首图、逐帖 ID、顺序和 AI 来源信息继续保留平台约束。

## 6. 异常与人工判断决策表

默认策略保持：**模型与图片调用不自动重试；正常阶段自动衔接。** Hands-off 不要求无限恢复；停下时必须告诉用户缺什么、可以怎样继续。自动格式校验等确定性步骤不能偷偷改写正文或冒充额外内容审核。

| 情况 | 系统自动处理 | 用户动作／继续规则 |
|---|---|---|
| 正常阶段完成 | 校验并衔接下一阶段，按所选图片策略处理 | 最终审阅；无需逐阶段确认 |
| 核心证据不足 | 暂停依赖该事实的下游，列出具体缺口 | 同任务补材料或明确调整说法，生成影响计划后继续；不猜数据 |
| 目的、资料或选项冲突 | 指出冲突项，保留已完成成果 | 用户明确取舍；不擅自改变目标读者、平台或写作目的 |
| 文本超时／调用失败／无效输出 | 保存实际错误、阶段、预算和有效上游 | 显示是否满足续接条件；符合则继续，不符则解释并带原资料新尝试。不能重开页面就重新消费调用 |
| 图片生成或视觉检查失败 | 保留正文与失败证据，不附失败图 | 显式重试、换用户图、同图复核或纯文字；每次调用独立留痕，不自动降级 |
| 某语言／平台失败 | 保留其他已成功分支；共享来源问题则标出受影响分支 | 从受影响分支继续，不能把另一平台成功当成本平台通过 |
| 登录、权限、额度或配置不足 | 给出操作者／维护者各自要处理的具体项 | 修复配置后显式继续；不默认购买服务、读取密钥或要求日常操作者进终端 |
| 版本冲突／旧图迟到／恢复导致过期 | 拒绝覆盖；标明当前修订和旧结果归属 | 刷新当前成果、重新检查影响或显式派生；不强制覆盖 |
| 服务中断／退出无法确认 | 标记 interrupted／待核对，保留预算与控制记录 | 按原快照显式恢复；不能创建重复活跃尝试 |
| 发布明确失败／串帖部分已发 | 保留平台 ID、已发前缀和错误 | 仅在发布器判定可继续时，针对剩余对象再次确认；不从头重发 |
| 发布结果未知 | 阻止自动重发，突出已知提交事实与核对入口 | 核对平台结果；不拿重新授权、改版本或恢复备份绕过 unknown 防重 |

不在本轮决定新的自动重试次数。未来若引入，须先明确错误类别、最大次数、总预算、取消／重启后的计数和用户可见记录，并更新本表及专项测试；平台 unknown 始终排除。现有超时与一次续接约束在新接口明确替代并验证前继续生效。

## 7. 可读依据视图的数据契约

前端至少需要以下语义信息，由读取层映射现有工件；缺少数据时显示“未记录／不可用／对应旧版本”，不能用通用成功卡片补齐。

| 视图 | 最小信息及版本要求 |
|---|---|
| 当前成果 | 任务／修订、平台／语言／对象、正文与图片状态、保存版本、发布状态、下一步原因 |
| 阶段时间线 | 尝试与阶段归属、开始／结束／预算、完成／失败／等待原因、可查看的实际产物；未开始阶段不标通过 |
| 材料与主张 | 来源名称与快照、实际读取范围、引用位置、正文 block／claim 关联；推断与直接依据区分 |
| 固定规则 | 名称、版本／hash、采用阶段与选项匹配原因；链接项目可读规则，不暴露执行提示全集或让用户挑 skill |
| 审核与修订 | 对应冻结稿、问题位置、证据、建议、实际修改前后片段、采纳／保留及理由、修订终稿关联；没有发现／没有修改如实展示 |
| 用户修改与图片 | 修改提案的源稿、接受状态、实际差异、受影响稿件；图片来源、正文绑定及检查结果；未检查与已检查不混用 |

定位必须校验文档 ID、版本、锚点与 hash；无法定位时回到对应旧稿并说明原因，不能把旧位置高亮到新正文。历史任务缺账本不回填虚构来源；显示已有稿与现存依据，并明确哪些能力需要显式新尝试。

技术 JSON 可保留在次级入口。原始正文、提示、审核内容仍遵循 tmp 边界，不为透明展示复制进正式执行日志。

## 8. 实施顺序与契约完成条件

1. **UX-03＋CORE-01 契约先行**：同一 owner 落实上述对象关系、状态／动作、失效规则、预算与并发语义；CORE-01 的共同任务契约前移，CORE-02 跨平台单母稿实现仍可后续。
2. **可并行设计**：UX-01／02 的展示和 UX-06 的文案可先设计；实际接入读写依赖统一契约。技能分析与外部资源准备不必等待体验实现。
3. **分包实施**：UI owner 负责成果、依据、配置；执行 owner 负责暂停与恢复；图片 owner 统一平台已有能力。共享 HTTP／类型／存储由整合 owner 汇总，不能各自发明一套任务状态。
4. **完整体验必需范围**：UX-01～03，以及 UX-04 图片策略、UX-05 恢复、UX-06 日常易用性与版本衔接都纳入四目标验收。CTA、全局预设、通知等未决选配项不成为阻塞项，也不擅自定案。
